# Hy3DMLX — mlx swift

MLX **Swift** port of Hunyuan3D image→mesh shape inference, for native macOS/iOS apps (Mac App
Store shippable — Metal runs in the App Store sandbox). The Python package in the repo root is the
parity reference; this Swift package re-implements the same modules against
[`mlx-swift`](https://github.com/ml-explore/mlx-swift), loading the **same `.safetensors` weights**.

## status — full image→glb pipeline, no python at runtime

Every stage runs in MLX Swift (or, for image decode, CoreGraphics — a host op even in the Python
reference). The whole path is sandbox-clean for iOS/Mac:

```
image file
  → Preprocess.swift   (CoreGraphics decode + alpha-recenter + ImageNet-normalize → NHWC)
  → DINOv2.swift       (DINOv2-giant ViT + SwiGLU conditioner)
  → Pipeline.denoise   (CFG flow-match Euler, 30 steps, calling DiT.swift)
  → VAE.swift          (post_kl → transformer → geo_decoder SDF)
  → Pipeline.gridSDFOctree (FlashVDM near-surface SDF field; `dense` flag forces full (R+1)³)
  → MarchingCubes.swift (lewiner-table isosurface; MCTables.swift baked constant; NaN-aware)
  → GLB.swift          (binary glTF writer)
```

### speed (2mini fp16, r256, this apple-silicon machine)

| grid path | grid stage | end-to-end | mesh |
|-----------|------------|------------|------|
| dense (R+1)³, ~17M pts | ~63 s | ~79 s | 152 592 v |
| **octree (FlashVDM)**, ~4.6% of pts | **~4–8 s** | **~17–34 s** | 152 592 v |

The octree decodes a coarse grid (63³), then refines only the near-surface band ×2 up to 256,
NaN-filling inactive cells. **~15× on the grid stage, ~4.5× end-to-end, near-lossless**
(octree↔dense Chamfer 0.0058 — same as the Python reference's own 0.0057). Both Swift and Python
run identical MLX Metal kernels, so this algorithmic win is the real performance lever; the host
language is not.

### per-stage parity vs the parity-verified python (`swift run hy3d-cli`)

| stage    | metric            | value        |
|----------|-------------------|--------------|
| DiT      | cosine vs Python  | 1.0000000    |
| ShapeVAE geo_decoder | cosine | 0.9999999    |
| DINOv2-giant | cosine        | 0.9999999    |
| marching cubes | verts vs skimage @R256 | 148852 == 148852 |
| end-to-end mesh (identical cond) | Chamfer | 0.0071 |

The neural compute is bit-identical. The one approximate stage is **image preprocessing** (pixel
cosine ~0.997): CoreGraphics/bilinear resampling differs from cv2's kernels, so the conditioning
is ~0.97 cosine and the full image→GLB mesh is Chamfer ~0.015 vs Python — **visually identical**.

### files

- `Layers.swift` — fp32 LayerNorm/RMSNorm, GELU tanh/erf, SiLU, SDPA, timestep embedding.
- `DiT.swift` — `Hunyuan3DDiT` (FLUX double/single stream, RMS QK-norm, no RoPE).
- `VAE.swift` — ShapeVAE decoder + cross-attention `geoDecoder` (Fourier embed → SDF).
- `DINOv2.swift` — DINOv2-giant ViT (patch conv, 40 layers, SwiGLU MLP, layer-scale).
- `Preprocess.swift` — image → ImageNet-normalized NHWC pixels (CoreGraphics + manual bilinear).
- `Pipeline.swift` — CFG flow-match denoise loop + dense (`gridSDF`) and octree (`gridSDFOctree`,
  FlashVDM near-surface refinement: `nearSurfaceMask` + 3×3×3 `dilate` + ×2 upsample + NaN-fill).
- `MarchingCubes.swift` / `MCTables.swift` — lewiner-table isosurface (tables generated by
  `scripts/generate_mc_tables.py`, baked as a constant — no runtime Python); skips NaN cells so it
  is octree-ready.
- `GLB.swift` — minimal binary glTF writer (POSITION + indices).
- `hy3d-cli/main.swift` — `swift run hy3d-cli` prints per-stage parity; `swift run hy3d-cli mesh [R]`
  runs the full image→GLB pipeline (default R=256) → `outputs/swift_demo.glb`.

## build & run

```bash
# one-time: the Metal toolchain is a separate Xcode component on macOS 26/27
xcodebuild -downloadComponent MetalToolchain

cd swift
swift run hy3d-cli                  # per-stage parity (DiT / VAE / DINOv2 / Swift-preprocess)
swift run -c release hy3d-cli mesh 256        # full image -> outputs/swift_demo.glb (octree, ~17s)
swift run -c release hy3d-cli mesh 256 dense  # force the dense grid path (~79s) for comparison
```

Parity fixtures (DiT/VAE/DINO inputs+outputs, and the denoise noise/sigmas) are dumped from the
Python reference via `scripts/dump_swift_fixtures.py`; the mesh path reads the bundled demo image
directly through `Preprocess.swift`.

## Hunyuan3D 2.1 shape (`DiT21`, DINOv2-large, existing `VAE`)

`ShapeGenerator` recognises 2.1 checkpoints by their weight names (`blocks.0.attn1.to_q.weight`) and builds
`DiT21` (Hunyuan-DiT, 21 blocks, MoE in the last 6) + `DINOv2` large (GELU MLP). The 2.1 VAE decoder is the
same network as before (no qkv bias, qk-norm, 4096 latents), so `VAE` is reused.

Per-module parity against the PyTorch reference (fp32 CPU; fixed random inputs; fp16 weights in Swift),
from `Tools/h3d21` (`h3d21 parity`; the XCTest host cannot read the external models drive):

| module | cosine | max abs |
|---|---|---|
| DINOv2-large `[1,1370,1024]` | 0.999998 | 0.064 |
| VAE decode `[1,4096,1024]` | 0.999999 | 1.0 (values ~O(100)) |
| VAE geo-decoder SDF `[1,2048,1]` | 1.000000 | 6.7e-5 |
| DiT21 `[1,4096,64]` | 0.999995 | 0.041 |

End to end (`h3d21 e2e 004 128`, same preprocessed pixels and noise, 30 steps, CFG 5, res 128): mesh Chamfer
vs the PyTorch reference mesh is 0.17% of the bounding-box diagonal (51,658 vs 51,693 vertices).
